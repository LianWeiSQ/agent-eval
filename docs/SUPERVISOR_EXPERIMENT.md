# 监督纠错对照实验

目的：区分“再次尝试本身带来的变化”和“监督反馈带来的额外效果”。当前平台提供所需接口，但在实验完成前不声明监督提高了通过率。

## 开始条件

- 固定同一 Benchmark 内容、执行模型、适配器版本、容器资源和官方时限。
- 样本先有一次正常执行和完整官方评分，排除环境、安装、适配和评分异常。
- 先用人工核查过的通过与失败样本校验监督快照；平台把矛盾 `pass` 转为 `uncertain` 不算模型校验成功。
- 预先登记任务范围、重复次数、执行和监督调用上限、缺失结果处理及允许的恢复次数。

## 两个重试分支

| 分支 | 输入与运行方式 |
| --- | --- |
| 直接重试 | 在全新容器中执行原始题面，不附加诊断建议 |
| 监督纠错 | Supervisor 审查首次证据；人工审核建议后，在全新容器中执行原题与获批反馈 |

两组使用相同执行快照和官方解题时限。Supervisor 的额外模型开销和人工审核时间单独记录，不能把相同执行时限描述成相同总成本。运行顺序应交错或随机化，以降低网络和主机负载偏差。

等全部基线执行结束并完成证据检查后再批量监督。首次成功、基础设施失败、监督缺失和人工拒绝均保留，不以补跑其他题替换。直接重试使用独立 Job，跨 Job 配对由实验记录维护。

## 人工审核

监督输入使用 `task-completion-v2`：`pass` 表示执行 Agent 完成任务，不能表示“同意官方零分”。若模型输出 `pass` 而 Trial 未通过，平台将其标记为 `uncertain` 并送人工复核，同时保留原始回复及校验原因。

Terminal-Bench 监督输入分别列出平台总等待、官方 Agent 解题和 verifier 评分时限。审核人应先查看具体建议与证据，再记录批准、修改、拒绝、接受当前结果或终止。反馈不得复制参考解法、隐藏测试代码或隐藏答案常量。

## 指标

- 首次、直接重试和监督纠错结果的官方二元 reward；
- 各组成功数、有效数、无效数和缺失数；
- 有效失败样本上的修复率与配对成功差异；
- 双方都成功、双方都失败、仅反馈成功、仅直接重试成功四类数量；
- 执行 Agent 与 Supervisor 的输入/输出 Token、耗时、工具调用和可得费用；
- 人工拒绝或修改原因、泄漏检查、监督调用失败和输出截断；
- 原始三类 verdict 的分布，以及平台拦截的 verdict 冲突数量。

页面“监督检出率”把原始 `fail` 和 `uncertain` 都视为对未通过结果的提示，并且监督可见官方评分，不能称为盲评准确率。失败和不确定结论必须完整保留，平台修复造成的改善也应与监督收益分开报告。
