# Eval 设计与实施路线

本文说明系统目标、设计选择与后续路线，不包含真实实验成绩。当前代码对应关系见 [架构说明](ARCHITECTURE.md)，操作边界见 [已知问题](KNOWN_ISSUES.md)。

## 要回答的问题

Eval 面向能够调用工具、操作文件和完成多步任务的 Agent，围绕三个问题组织评测：

1. **任务表现**：在固定环境、工具和时间预算下，执行 Agent 能否完成任务？
2. **证据可信度**：失败来自 Agent、运行环境、适配器还是评分器，成绩是否有完整证据支持？
3. **纠错收益**：监督建议经人工审核后，是否比无反馈再试一次更有效，增加的时间、Token 和人工投入是多少？

流程可运行不等于监督有效。平台的目标是让“执行、证据、评分、监督、人工决定和重试”均可追溯，再通过受控实验回答收益问题。

## 角色与边界

| 角色 | 责任 | 当前实现 |
| --- | --- | --- |
| Benchmark | 定义任务、初始环境、完成要求和评分依据 | MMLU 20 题；固定官方提交的 Terminal-Bench 2.1 |
| 执行 Agent | 使用模型与工具完成任务，提交输出与产物 | Harbor Codex 为默认主路径；DSH 为可选配置 |
| Eval 平台 | 固定配置、调度、采集证据、组织评分与审核、生成报告 | Portal、REST API、CLI、SQLite 与文件存储 |
| 运行环境 | 准备独立环境，执行 Agent 和官方测试 | Harbor + Docker Linux 容器 |
| 评分器 | 检查答案、文件或程序行为是否满足要求 | Terminal-Bench 官方 verifier；MMLU 答案规则 |
| 监督 Agent | 根据可观察证据诊断问题并提出建议 | 独立 `llm-supervisor` Adapter |
| 人工审核人 | 审查、修改或拒绝反馈，决定是否重试 | 带理由和审计记录的纠错决定 |

监督意见不能替代官方任务成绩，也不能自行批准重试。MMLU 与 Terminal-Bench 测量不同能力，结果分别报告。

## 目标流程

```text
固定 Benchmark 与 AgentSnapshot
  -> Attempt 1 在独立环境执行
  -> 保存轨迹、输出、产物与用量
  -> 官方或规则评分，并验证证据边界
  -> 按实验计划触发独立监督
  -> 人工审核具体建议
  -> 获批反馈在全新环境创建 Attempt 2
  -> 与首次结果及无反馈直接重试做配对分析
```

当前单个 Job 的执行、评分、监督、人工决定和纠错 Attempt 已接通。监督需显式触发；直接重试对照使用独立 Job，跨 Job 配对和实验汇总目前由实验侧维护。

## 可追溯对象

| 对象 | 保留内容 |
| --- | --- |
| Benchmark | 来源、固定提交、任务与评分资源摘要 |
| AgentSnapshot | Agent、模型路由、预算、运行包与适配代码摘要 |
| Job | 任务筛选、快照、重复次数、并发与门槛 |
| Trial / Attempt | 输入、状态、成绩、失败阶段和父尝试关系 |
| AgentRun / Artifact | 事件、工具参数与结果、产物与用量 |
| SupervisionRun | 原始回复、解析结果、引用、配置与用量 |
| CorrectionDecision | 审核人、决定、理由、最终反馈与子尝试 |
| Report | 有效/无效数量、首次表现、纠错效果与成本 |

修改执行条件后创建新快照；后续尝试不覆盖首次结果。在线模型、网络和依赖服务仍可能产生不可复现差异，版本摘要不能消除这些变量。

## 可信评分

环境未准备、Agent 未安装、题面未正确传入或 verifier 未完整执行时，结果归入对应基础设施或适配异常，能力分数留空。正常达到解题时限后，平台先终止并确认 Agent 相关进程停止，再运行官方测试。

Terminal-Bench 保存原始 reward、可采信 reward、完整测试报告和失败阶段。整题只有官方二元 reward 通过才计为成功；部分测试通过不等于整题通过。每个 Trial 的容器、网络和卷结束后销毁，预构建镜像保留为跨任务缓存。

## 监督与人工审核

监督读取题面、规范化轨迹、工具结果和官方评分理由，不把参考答案、参考解法或隐藏测试作为独立输入字段。评分理由和工具输出仍可能含参考信息，因此人工审核需继续检查答案泄漏风险。

`task-completion-v2` 规定：

- `pass`：证据支持执行 Agent 完成了任务；
- `fail`：证据支持任务未完成，即使官方零分判定正确；
- `uncertain`：证据不足或存在无法消解的矛盾，需要人工复核。

若监督原始 `pass` 与 Trial 未通过冲突，平台保留原回复并转为 `uncertain`。该保护不能计作模型自己检测成功。网络错误、输出截断和无效 JSON 属于调用失败，不是有效的 `uncertain` 结论。

监督可以看到官方评分，因此当前统计不是盲评准确率。人工修改反馈后，实验结论对应“监督加人工审核”的共同效果，不能只归因于监督模型。

## 验证监督收益

对有效失败样本至少比较三个条件：首次执行、干净环境下无反馈直接重试、干净环境下使用获批反馈重试。固定执行快照、官方时限和资源配置，并记录双方都成功、都失败、仅反馈成功和仅直接重试成功四类配对结果。

Supervisor 和人工审核会增加成本。实验应预先登记任务范围、重复次数、失败调用重试规则、预算和缺失结果处理，并单列无效运行、调用失败、Token、耗时和人工投入。详细方法见 [监督纠错对照实验](SUPERVISOR_EXPERIMENT.md)。

## 分阶段实施

| 阶段 | 状态与验收方向 |
| --- | --- |
| 核心平台 | 本地执行、评分、轨迹、监督、审核和纠错链路已具备 |
| 可靠性 | 容器清理、超时、阶段分类和证据校验已覆盖；长轨迹与外部接口恢复仍需完善 |
| 受控实验 | 方法与接口具备；总体监督收益尚未验证 |
| 服务化 | 可信认证、持久队列、共享 Artifact 和跨主机恢复仍是后续工作 |

仓库只保存平台代码、测试、通用配置和准备配方。任务源缓存、Docker 镜像、数据库、模型输入输出、轨迹、真实报告、凭据和本机运行包保留在代码仓库之外。
